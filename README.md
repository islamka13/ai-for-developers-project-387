# Календарь звонков

[![hexlet-check](https://github.com/islamka13/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/islamka13/ai-for-developers-project-387/actions)

Сервис бронирования времени по мотивам Cal.com. Владелец календаря публикует доступное время для встреч, гость выбирает свободный слот и записывается на звонок — без регистрации и авторизации.

Этот репозиторий продолжает первый проект: приложение перенесено без старой истории Git, а процесс разработки автоматизируется в GitHub Actions.

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Роли

- **Владелец календаря** — один заранее заданный профиль. Заводит типы встреч и смотрит список предстоящих встреч.
- **Гость** — любой посетитель без аккаунта. Выбирает тип встречи и бронирует свободный слот.

## Сценарий: от создания типа встречи до записи в списке владельца

### Владелец

1. Владелец открывает админскую страницу и создаёт тип встречи: задаёт название (например, «Знакомство»), описание и длительность в минутах (например, 30).
2. Тип встречи сохраняется и становится доступен гостям на странице записи.

### Гость

3. Гость заходит на главную страницу и переходит на страницу записи.
4. Видит каталог типов встреч: название, описание и длительность каждого типа.
5. Выбирает тип встречи — открывается календарь на ближайшие 14 календарных дней.
6. Видит свободные слоты в рабочие часы владельца. Длительность слота равна длительности выбранного типа встречи.
7. Выбирает свободный слот и подтверждает запись.
8. Получает подтверждение бронирования. Если слот уже занят (в том числе встречей другого типа), видит понятное сообщение о конфликте.

### Владелец (проверка)

9. Владелец открывает страницу предстоящих встреч и видит новую запись в общем списке встреч всех типов.

## Ограничения

- Нет авторизации, личных кабинетов и интеграций с внешними календарями.
- Одно и то же время нельзя занять дважды, даже разными типами встреч. Примыкание допустимо: следующая встреча может начинаться в момент окончания предыдущей.
- Окно записи — 14 календарных дней, сдвигается с текущей датой. Начало окна, рабочие часы, часовой пояс и шаг доступных стартов фиксируются в спецификации.
- Данные хранятся в памяти процесса: перезапуск приложения сбрасывает записи.

## Стек

- **Фронтенд:** React + Vite + TypeScript, shadcn/ui
- **Бекенд:** Hono (TypeScript)
- **API-контракт:** TypeSpec → OpenAPI → клиентский SDK для фронтенда
- **Публикация:** Docker-образ, деплой на Render

## Установка

Требуется [mise](https://mise.jdx.dev/) — он ставит Node.js и остальные инструменты версий из `mise.toml`.

```bash
git clone https://github.com/islamka13/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise install        # инструменты
mise run install    # npm-зависимости
hk install          # git-хуки (pre-commit запускает проверки)
```

## Использование

```bash
mise run dev     # фронтенд http://localhost:5173, API http://localhost:3000
mise run check   # все проверки: линтер, типы, тесты (как в CI)
mise run build   # продакшен-сборка фронтенда
npm run start -w server   # запуск собранного приложения (порт из PORT, по умолчанию 3000)
```

## Docker

Образ собирается из `Dockerfile` в корне репозитория:

```bash
docker build -t booking-service .
docker run --rm -p 3000:3000 -e PORT=3000 booking-service
```

Приложение стартует внутри контейнера автоматически и слушает порт из переменной окружения `PORT` (по умолчанию 3000). В образе уже собран фронтенд: сервер раздаёт `web/dist` и API с одного origin.

## Деплой

Публичная ссылка: **https://booking-service-wdcu.onrender.com**

Деплой делается агентом через MCP-сервер Render. Его проектная конфигурация лежит в `opencode.json` (OpenCode V2, `mcp.servers`), секретов в файле нет:

1. Создайте API-ключ в [настройках аккаунта Render](https://dashboard.render.com/u/settings#api-keys) с доступом к нужному workspace и задайте переменную окружения `RENDER_API_KEY` (например, `setx RENDER_API_KEY "ключ"` в PowerShell). OpenCode официально не поддерживает OAuth для Render, поэтому используется ключ из окружения. Сам ключ в Git не попадает: `opencode.json` хранит только ссылку `{env:RENDER_API_KEY}`.
2. Перезапустите OpenCode и проверьте `/mcps` — рядом с `render` должно быть `connected`.
3. Попросите агента выбрать workspace Render и создать web service из Dockerfile этого репозитория. Переменную `PORT` задаёт платформа; приложение читает именно её.
4. После выката проверьте по публичной ссылке сценарий гостя и владельца: создать запись, увидеть её в списке предстоящих встреч и убедиться, что повторная запись на занятый слот отклоняется.

Бесплатный тариф Render засыпает после 15 минут без запросов, поэтому первый запрос после паузы отвечает дольше обычного.

Данные хранятся в памяти процесса и **сбрасываются при каждом перезапуске** — в том числе при рестарте сервиса после сна и при выкате новой версии. Постоянного хранилища в проекте нет (ADR-0002).

## Агент в GitHub Actions

Основной воркфлоу — `.github/workflows/opencode.yml`. У него две job:

- `opencode` — ручной вызов комментарием `/oc` или `/opencode` (`mentions: /opencode,/oc`) на событиях `issue_comment` и `pull_request_review_comment` с типом `created`: комментарий к задаче, к обсуждению PR или к строке diff.
- `triage` — автоматический предварительный разбор новых обращений на событии `issues` (`types: [opened]`). Инструкция лежит в `prompt` job, потому что у этого события нет комментария с командой.

Агент запускается только для доверенных авторов (`OWNER`, `MEMBER`, `COLLABORATOR`, не бот); комментарии ботов и PR из forks секрет модели не получают. Автотриаж дополнительно пропускает уже подготовленные тикеты: issue с метками `ready-for-agent` или `ready-for-human` (их создаёт `to-tickets`) повторно не разбирается.

- **Модель:** `opencode/big-pickle` (бесплатная модель консоли OpenCode). Ключ лежит в секрете репозитория `OPENCODE_API_KEY` (пространство OpenCode `Hexlet Students`). Набор доступных моделей задаётся в консоли (`Console → workspace → Models`), а конкретная модель для агента фиксируется в репозитории: `model:` в воркфлоу и `small_model` в `opencode.json`. В локальном TUI модель выбирается командой `/models`.
- **Сессии:** `share: true` — публичные, это решение принято до первого вызова.
- **Авторизация:** стандартный режим GitHub App через OIDC. Воркфлоу имеет `contents: read` и `id-token: write`, `actions/checkout` использует `persist-credentials: false`; комментарии и push делает приложение.
- **Ограничения:** `timeout-minutes: 15` для ручного вызова и `10` для автотриажа, общий `concurrency` по номеру issue/PR, устаревшие запуски не отменяются (`cancel-in-progress: false`), чтобы не расходовать попытки зря.
- **Настройки агента:** скиллы `to-spec`, `to-tickets`, `implement-spec` и `triage` доступны из `.agents/skills/`; трекер описан в `docs/agents/issue-tracker.md`, правила — в `AGENTS.md`.
- **Конфиг `opencode.json`:** формат OpenCode V1 (в Actions сейчас 1.19.6). `small_model` явно выставлен в `opencode/big-pickle`, иначе для заголовка сессии берётся недоступный `gpt-5.4-nano` (403). Внешние каталоги разрешены общим правилом `external_directory: allow`: точечные исключения для путей раннера не спасают, когда агент исследует внутренности экшена, и в неинтерактивном раннере это выглядело как зависание; `bash` в этом воркфлоу и так разрешён на `*`. `doom_loop` запрещён.

Результат виден в обсуждении issue/PR (ответ агента, коммиты и PR) и на вкладке **Actions → opencode**.

### Независимое авторевью

`.github/workflows/opencode-review.yml` срабатывает на `pull_request` (`opened`, `synchronize`, `reopened`, `ready_for_review`) отдельно от сессии реализации. Критерии лежат в `REVIEW.md` и передаются ревьюеру вместе со spec-issue #6, тикетами #7/#8, комментарием согласования и diff. Ревьюер работает через неинтерактивный CLI V1 (`opencode-ai@1.19.6`) и не меняет код: файловые и bash-инструменты отключены, комментарий публикуется отдельным шагом через `gh pr comment` с `GITHUB_TOKEN`. OIDC для этой job не нужен.

Ревью запускается только для веток этого репозитория и доверенных авторов, а также для PR от `opencode-agent[bot]` — PR агента тоже должен рецензироваться. Общий фильтр ботов здесь не применяется, но PR из fork не получают секрет модели. У job есть `timeout-minutes: 10` и `concurrency` по номеру PR с отменой устаревших запусков. Шаблон `.github/pull_request_template.md` требует заполнить проверки (команды, ссылки на прогоны, SHA), риск и способ отката. Решение о мерже остаётся за человеком.
